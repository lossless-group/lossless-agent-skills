# The LFM Skill Knows About npm and the Browser Entry

## Why Care?

Agents in Claude, ChatGPT and Claude Code were told LFM lives only on JSR, which the public CDNs don't serve. So an agent asked to preview a memo as a work artifact had no way to load LFM and would render the markdown its own way, with its own citation numbers. Since 0.11.0 the package is on npm, jsDelivr serves `@lossless-group/lfm/browser`, and the skill now says so.

## What changed

- **`SKILL.md`**: npm joins JSR as a no-auth install. A new "Quick render in a browser" section gives the pinned jsDelivr import, the parse-then-convert rule, and the rule never to write citation numbers. The description now triggers on rendering LFM in a browser page or Claude artifact. The package's home is updated to its own repo, `lossless-monorepo/lfm/`.
- **`references/package-and-setup.md`**:
  - a registries table (npm, JSR, GitHub Packages), and the `.npmrc` scope trap that routes an npm install to GitHub Packages;
  - a section on `/browser`: what it leaves out (Open Graph fetching, Shiki, PlantUML), the CDN URLs, a full HTML example with a sources list, and the known chaining issue;
  - the release process as it is now: version in `package.json` and `deno.json`, notes in `changelog/releases/`, one `v*` tag running `publish-jsr.yml` and `publish-npm.yml`, the local `lfm:*` scripts, and npm trusted publishing;
  - the `pnpm-workspace.yaml` that both CI's pnpm 9 and local pnpm 12 accept;
  - troubleshooting rows from the first npm publish (a 404 that meant an expired login, `ERR_PNPM_IGNORED_BUILDS`, `packages field missing or empty`, CDN lag).

## Not changed

The Astro integration, trigger-map and co-development sections still describe `astro-knots/packages/lfm` and an `lfm-astro` integration config that predate LFM's own repo. A note in the publishing section flags the move; those sections need their own pass.
