# Every New Splash Ships With Analytics

## Why Care?

We put OpenPanel on every splash in May, then kept building splashes. The
skill agents follow to build one never mentioned analytics, so none of the
newer ones had it: augment-it, dididecks-ai, lossless-agent-skills, id-didi-sh,
flave and hope-ai all went live with no way to tell whether anyone visited.
That went unnoticed for six months.

A one-time audit fixed those six. This change is what keeps the next one from
shipping blind.

## What's New?

- **Analytics is part of building a splash.** Step 8 of the scaffolding flow,
  which adds the Pages workflow, now hooks up analytics in the same pass, and
  the acceptance checklist won't pass a splash whose live page doesn't send an
  accepted event.
- **The provider comes from a config, not the skill.** The skill reads
  `config/private.json` for the provider, the skill that wires it, the
  build-time variable, how to name the client and which origin to allow. The
  Lossless Group's config says OpenPanel; another team's can say Plausible,
  Umami, Fathom or none. Without a config the agent asks once and offers to
  save the answer.
- **The splash-specific steps are spelled out:** the component in the layout's
  head, the `env:` line on the workflow's build step (merged into an existing
  `env:` block, not a second one), the repo Variable, and a test event from the
  allowed origin. The provider's own skill still owns the details.
- **A lesson records why:** a step in the scaffolding flow is what fixes the
  future, because an audit only fixes the past.

## Under the Hood

- Same config pattern as `hubspot-interface` and `augment-speakers-panelists`:
  `config/private.example.json` is committed and documents the shape;
  `config/private.json` is gitignored.
- Only the tracking ID goes in a site or a repo Variable. The skill tells
  agents not to store the provider's secret anywhere, since a browser tracker
  never uses it.
