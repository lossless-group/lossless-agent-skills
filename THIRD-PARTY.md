# Third-Party Skills and Skill Packs

How The Lossless Group pulls in skills someone else wrote, and how our own skills
depend on them. This file is the one place the rule lives; other docs point here.

**Status: Draft.** The shapes below describe what the tree already does as of
2026-11-19. Expect them to change as we publish more of our own skills.

## Pick the shape by what the upstream repo is

| Situation | How to pull it in | Where | Examples |
|---|---|---|---|
| The repo is a ready skill folder (or several), and we'll **load** it | Submodule. Fork it under `lossless-group` first if we'll change it; add upstream read-only if we won't. | This repo, `<name>/` | `humanizer`, `talk-normal` (forks); `archify`, `chroma-agent-skills` (upstream) |
| The skill is **generated by an installer or package**, so the repo has no `SKILL.md` folder to point at | Commit the installed output, plus a `VENDORED.md` with source, version, and refresh steps. A fork is optional, as a stable source to refresh from. | This repo, `<name>/` | `graphify` |
| A pack we'll **mine** for our own skills, not load | Submodule, not linked into any harness | The repo that needs it, under `context-v/skill-packs/<pack>/` | `seo-skills` in astro-knots |
| **Reference material** for a study | Submodule | `ai-labs/studies/<study>/` | `anthropics/skills`, the ADHD and executive-function repos |
| A skill only **one project** uses | Submodule | That project's `context-v/agent-skills/<name>/` | `neon` in fantasy-gm |

"Clone it in" always means `git submodule add`, never a plain `git clone`. A plain clone
leaves an untracked repo inside the parent, which nothing records.

## Fork or upstream?

- **Fork** (`lossless-group/<name>`) when we will patch it, or want it to survive the
  upstream disappearing or renaming. Pull upstream changes into the fork; never edit a
  copy elsewhere.
- **Upstream, read-only** when we use it as published. Never commit inside these: a
  local commit leaves a gitlink pointing at a SHA no remote has. Update by moving the
  submodule pointer.

## Our own skills that depend on a third-party one

Name the dependency in our `SKILL.md` (which skill, and what we use it for) and let the
harness load it. Don't copy its instructions into ours: the copy drifts the moment
upstream changes. If we only need one idea from it, write that idea in our own words
and cite the source.

## Loading

- A submodule whose `SKILL.md` sits at its root links like any of our skills.
- A submodule whose `SKILL.md` sits deeper (`archify/archify/`, `talk-normal/skill/`,
  `chroma-agent-skills/skills/<name>/`) needs an entry in `.stow-local-ignore` and a
  hand-made link, or a `NESTED_SKILLS` entry in `sync-skills.sh`. See `AUTHORING.md`.
- Skill packs under `context-v/skill-packs/` are never linked.

## Record it

Every third-party skill or pack gets a row in two tables, with its upstream:

1. The **Skills** table in this repo's `README.md`, if it lives here.
2. The **Third Party Agent Skills** section of the root `lossless-monorepo` README,
   wherever in the tree it lives.

A vendored copy also keeps its `VENDORED.md` current: source, version, date, refresh
steps.
